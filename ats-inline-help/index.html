Show relevant help using a stable page code

Engineering preloads the page code, description and location. Content editors find the help entry through a searchable category hierarchy and manage its content and status. The header listener identifies the page code; active guidance is selected for the current ATS login and customer system.

Proposed acceptance checks

  • A content editor can find the page through its category path or search.
  • The page code is read-only and is independent of URL changes.
  • Inactive help does not appear in the ATS.
  • An ATS login receives generic help for the current page.
  • Only selected roles receive the additional role guidance.
  • Only selected systems receive the single bespoke content section.
  • Preview shows the applicable sections for the selected role and system.
  • Actual pages are checked for content, tables, punctuation and character encoding.

Testing and improvement

Testing was initially manual in a test system and client development environment. Checking page associations required visiting the pages. I later introduced an in-place management preview; checks on the actual pages remained necessary. Content and formatting problems, including character-encoding issues on some host pages, were identified during testing.

Delivered and planned

The first release delivered generic contextual help to reduce duplicated documentation. Categorisation and permissions followed as the feature evolved. Management preview and embedded YouTube videos were later additions. The third phase of development was put on hold to prioritise other development. A separate knowledge base was developed later to support a broader range of projects.

Brian Turner · Project information

ATS Inline Help System

The problem

When I joined Recruitive, customer help and system documentation was largely produced as separate Word and PDF documents for each ATS customer. The team spent days assembling material that was repeated across systems and difficult to keep up to date. Customers had to wait for it. The work was demoralising because it was laborious and staff knew much of the documentation went unused.

My decision and role

At Zero-One Design, I had already designed and delivered inline help throughout our recruitment systems. Users could get guidance in the part of the system they were using. I demonstrated that approach to Engineering and specified how we could apply it to the ATS, despite the different frameworks.

I designed the management workflow, UI and page placement, specified the behaviour, tested it and oversaw delivery and later improvements. Engineering implemented the software. A member of my team worked on preparing and adding the content.

What we delivered

The first release focused on generic contextual help to reduce duplicated documentation. Content was initially associated with a page URL. We transferred existing material into the system and developed image management for the content editor. The feature became standard across all new ATS systems as the shared content grew.

The page association later evolved to a continuous listener in the header using a unique page code supplied by Engineering. Content editors could not change that code. Categories and search helped staff find the right entry; permissions and system-specific content supported different audiences and customer needs.

Testing and improvement

We initially tested manually in a test system and client development environment. To check that help was associated with the right page, we had to visit it. I later introduced an in-place preview within help management, although the actual ATS pages still needed checking.

Those checks caught content and formatting issues, including tables and punctuation. They also exposed character-encoding problems on some host pages, where symbols such as ampersands did not display correctly. Checking UTF-8 handling was therefore relevant to the surrounding pages as well as the help content.

Results and learning

The biggest benefit was the time saved producing documentation common to most customers. That gave us more capacity for richer guidance, including embedded YouTube videos throughout relevant pages.

Bespoke functionality on standalone customer systems remained harder to support with reusable content. That reinforced the case for moving towards a multi-tenant model, where shared functionality, configuration and associated help could be managed centrally. Reducing bespoke development was the intention, although some customer requirements still needed it.

Further development

The third phase was intended to develop the help into a fully interactive, searchable knowledge base, reducing the need for whole-system video training and focusing new content on bespoke items or specific user groups. This phase was put on hold to prioritise other development. A separate knowledge base was developed later to support a broader range of projects and linked into the ATS.
